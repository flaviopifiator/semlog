# Security Policy

## Supported Versions

Before the first `1.0` release, only the latest published release receives
security fixes. After `1.0`, the latest minor release line receives fixes.

## Reporting a Vulnerability

Report security vulnerabilities through GitHub's private vulnerability
reporting: open this repository's **Security** tab and select **"Report a
vulnerability."** Do not report security issues through public GitHub
issues.

We aim to send an initial response within **14 days** of a report. After
triage, we coordinate disclosure through a GitHub Security Advisory, and
request a CVE through GitHub when applicable.

## Scope

This policy covers the semlog library's code and its published release
artifacts. Sinks, pipelines, and infrastructure operated by an adopting
organization around its own use of semlog are out of scope for this policy.

## Verifying releases

Releases are published to PyPI only through Trusted Publishing, with no
long-lived API token stored anywhere. Two GitHub Actions workflows publish,
`tag.yml` and `release.yml`, and both wait for a maintainer to approve the
protected `pypi` environment. [RELEASING.md](RELEASING.md) describes how
each of them publishes.

Each published file carries a PEP 740 attestation generated by
`pypa/gh-action-pypi-publish`. The attestation lets you verify that a
downloaded distribution was built and published by one of those workflows:

```bash
pip install pypi-attestations
pypi-attestations verify pypi --repository https://github.com/flaviopifiator/semlog pypi:semlog-<version>-py3-none-any.whl
```

`pypi-attestations` is a third-party tool that you install yourself; semlog
neither uses nor depends on it. `pip` and `uv` do not verify these
attestations automatically at install time: verification is a step you run
yourself.
